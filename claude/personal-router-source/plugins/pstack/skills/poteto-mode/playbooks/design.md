# Design

1. Run `worktree` before repository edits.
2. Link every file in replies by its full path. Run `grill-with-docs` to frame the screen. Settle its job, every state, every data case, and what is out of scope. Map the flow: every way into the screen, every way out, and what the user taps at each step. Write `brief.md` in `docs/design/research/<feature>/` from [design templates](../references/design-templates.md). Open one tracking ticket in the tracker named in the project's `docs/agents/issue-tracker.md`, titled `Design: <feature>`, with the `design` label, linking the brief. Create the label when it is missing. Work in words only through step 3. Done when every brief section is filled or listed under Open questions, the flow map names every way in and out, and the tracking ticket exists.
3. Run `research` on the brief. Use the Mobbin connector's screen search for layouts and its flow search for multi-step paths and transitions, Apple Human Interface Guidelines and Material Design motion guidance, and usability research such as Nielsen Norman Group and Baymard Institute. Write `findings.md` next to the brief, with one section per open question and a Flow and motion section. Directions are compared at desktop width, so collect desktop references: set Mobbin searches to the web platform and keep examples shown at desktop width. Add a mobile example only when it answers the phone-fit question, and label it mobile. Save example screens in `refs/`. Give each pattern its apps and links, when it works, its tradeoffs, and its fit with the project's design system. Mark motion read from still frames as inferred. Stop and wait for the user to mark what they like and dislike. Done when every open question has at least two patterns with examples and the user has marked the findings.
4. Build three directions from the findings. A direction is one complete layout built from the patterns the user liked. In the project's Paper file, build each direction on the Explorations page as one desktop board (1440 px wide), from the project's design tokens, with a short note on how its layout fits a phone, so a layout that cannot shrink is caught before the user picks. Ask the user to open Paper when it is not running. Run `arena` when one direction needs competing candidates. Critique each board with `impeccable` before the user sees it. Show each board in the chat: export it from Paper as a PNG image and embed the image in the reply, so the user can choose without opening Paper. Show every page of every direction; when directions share a page, show it under each and label it, such as "same as Direction 1". Record the three directions in the brief under Directions. Stop and wait for the user to pick one direction or ask for changes; repeat until one direction wins.
5. In Paper, build the winning direction's tablet (768 px) and mobile (390 px) boards from its desktop board. Show the three sizes in the chat as exported images, labeled, and wait for the user's approval. Then run `prototype` for the winning direction: a clickable throwaway page that walks the whole flow map with real transitions at all three widths, using the project's motion durations and honoring `prefers-reduced-motion`. Review the motion with `impeccable`. When showing the prototype, explain the motion in plain words: which click gets which motion, and that the motions are one set to approve, not options to choose from. Done when the user approves the boards and the prototype.
6. In Paper, build every state and data case from the brief on the winning direction, at desktop, tablet, and mobile, and show each board in the chat as an exported image. Write `motion.md` next to the brief from [design templates](../references/design-templates.md), with one row per transition in the flow map. Move each approved board to the Approved page under a `<Feature> · Chosen design` header with `move_nodes`. Stop and wait for the user to confirm that every state has a board and every transition has a motion row.
7. Run `to-spec`, then `to-tickets`. Export the approved boards and link them under [Planning](planning.md) step 6, and link `motion.md` in each screen ticket's `## Design` section. Close the tracking ticket with links to the specification and tickets. Land every design file (the brief, findings, references, `motion.md`, the prototype, and the exported boards) in one docs-only PR through [Opening a PR](opening-a-pr.md), and link the files by their `main` paths in the tickets. Tell the user that the tickets wait until that PR merges. Recommend the next implementation playbook under the shared handoff rule. Done when every ticket that changes a screen links its boards and motion rows, and the design PR is open.
