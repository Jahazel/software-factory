# Design

1. Run `worktree` before repository edits.
2. Link every file in replies by its full path. Run `grill-with-docs` to frame the screen. Settle its job, every state, every data case, and what is out of scope. Map the flow: every way into the screen, every way out, and what the user taps at each step. Split the screen into sections, such as header, week list, and empty state, and order them so each section builds on the ones before it. Write `brief.md` in `docs/design/research/<feature>/` from [design templates](../references/design-templates.md). Open one tracking ticket in the tracker named in the project's `docs/agents/issue-tracker.md`, titled `Design: <feature>`, with the `design` label, linking the brief. Create the label when it is missing. Work in words only through step 2. Done when every brief section is filled or listed under Open questions, the flow map names every way in and out, the section order is set, and the tracking ticket exists.
3. Build the running prototype: one isolated route that follows the project's routing convention, such as `/prototypes/<feature>`. Nothing links to it, and production code never imports from it. It renders the screen from the project's design tokens with realistic data. Its frame shows one screen size at a time, at full size inside a scrollable frame. A toolbar at the top switches between desktop (1440 px), tablet (768 px), and mobile (390 px), and also between full motion and reduced motion. Desktop and full motion are the defaults. The URL keeps the choices, such as `?size=desktop&rm=0`, so a reload or a shared link opens the same view. The frame honors `prefers-reduced-motion`. Start the dev server and give the user the route's local URL. Done when the route loads at each size from the toolbar with a clean console.
4. Build the screen one section at a time, in the brief's order. Done when every section in the brief is recorded as approved. For each section:
   - Run `prototype-variants` for the section: three variants, each on a named axis, inside the running prototype's context so the approved sections sit around it. Choose each variant's motion with `animate`; when several parts move together, order them with `choreograph`. Critique each variant with `emil-design-eng` and fix its findings before the user sees it.
   - Show the variants in the chat: a screenshot of each at desktop and mobile, its name, its axis, when it wins, and what it costs. Give the picker's URL. Stop and wait for the user to pick one, ask for a new round around one (`riff`), or ask for changes.
   - Move the picked variant into the running prototype. Show the prototype in the chat at all three widths and give its URL. Make the user's change requests in the running prototype and show the result each time, until the user says the section is done.
   - Run `break-ui` on the section. Fix what breaks in the running prototype and show the worst-case screenshots.
   - Record the section in the brief under Sections: the picked variant, its axis, and the user's reason. Then start the next section, or go to step 5 after the last one.
5. Finish the whole screen in the running prototype. Build every state and data case from the brief, and make every path in the flow map clickable with its real transition. Run `mobile-native` on the mobile width. Run `review-animations` on the prototype's motion and fix its findings. Write `motion.md` next to the brief from [design templates](../references/design-templates.md), with one row per transition in the flow map, each row's values chosen with `animate`. Explain the motion in plain words: which click gets which motion, and that the motions are one set to approve, not options to choose from. Then show the final prototype: give its URL, show every state at all three widths in the chat, and list each path to click so the user can feel every motion. Stop and wait for the user to approve the final prototype, its motion included. Make each change the user asks for in the prototype and show it again. Do not start step 6 until the user approves.
6. Run `to-spec`, then `to-tickets`. Save screenshots of every section and state at all three widths to `docs/design/<feature>/`. Add a `## Design` section to each screen ticket that links its screenshots, its `motion.md` rows, and the prototype route, so coding sessions build from those files. Give the last screen ticket the job of deleting the prototype route. Close the tracking ticket with links to the specification and tickets. Land every design file (the brief, `motion.md`, the screenshots, and the prototype route) in one design PR through [Opening a PR](opening-a-pr.md), and link the files by their `main` paths in the tickets. Tell the user that the tickets wait until that PR merges. Recommend the next implementation playbook under the shared handoff rule. Done when every ticket that changes a screen links its screenshots and motion rows, and the design PR is open.

A pick never changes production code. Production changes come only from the tickets, through an implementation playbook.
