# Shared conditions

- Start at the first needed step. Reuse current findings and let each skill handle its internal calls.
- Check `git log` and `git blame` when a proposed change depends on an earlier design decision. Reuse existing findings. Git history explains constraints; it does not replace evidence that a bug occurs.
- Apply the installed `principle-fix-root-causes` when debugging, within the authorized task scope. Keep `diagnosing-bugs` as the Bug fix workflow. The principle supplies guidance; it does not replace that workflow or authorize fixing unrelated instances.
- Apply the installed `principle-attack-the-premise` when two fixes that rest on the same assumption have failed the same check. Write the assumption down and test it before a third fix.
- Apply the installed `principle-test-behavior-not-implementation` when writing, changing, or keeping a test, also outside `tdd`. A test must fail when the behavior it checks is removed.
- Apply the installed `principle-prove-it-works` before reporting a task, step, or helper result as done. Check the real result, not a successful build, a proxy, or a self-report.
- Keep actions within the task's authorization. A required blocked check stays incomplete.
- Independent code reviewers must not have written the change. Review committed changes against the review base: the branch the pull request targets, from its GitHub copy. Without a pull request, use `main`. Run each reviewer as a fresh Claude Code process, not as a sub-agent of the session that wrote the change: `claude -p --model claude-opus-5-5 --effort high --permission-mode plan --no-session-persistence` (inside the git repo, prompt on stdin). If it cannot run, keep the review incomplete and say so.
- Rechecks: while working, run the type check and the changed test files. Run the full test suite once before the first commit. When the project's pre-commit hook runs the full suite, that commit is the run; run by hand only the suites the hook skips. Check `git status` and stage explicit paths before each commit. After a cleanup or fix, run `verify` again only when the change since its last passing run alters runtime behavior. Otherwise record that run as reused, with its revision, the changed files, and the reason. A project `verify` skill with its own reuse rule applies that rule.
- Small changes: use the definition in [the entrypoint](../SKILL.md#check-task-size-first). For a small change, skip the comment rules, `deslop`, `create-verification-skill`, and independent `code-review`. Record each as not applicable with the reason "small change". Still run the affected tests and code checks, and run the project's own `verify` skill only when the change affects a user-visible path. A change that does not meet every test above is medium or big.
- Medium changes: a change is medium when it is not small, touches about 5 files or fewer, changes about 200 lines or fewer, does not change how other code calls a function, and does not touch security, privacy, money, authentication, or stored data. For a medium change, the main agent does all of the work itself and starts no helpers except the reviewer and the comment helper. It reads the code directly instead of running `how`. It implements without delegation. It runs the comment rules as [the entrypoint](../SKILL.md#non-negotiables) describes, runs `deslop`, runs the affected tests and code checks, and runs `verify` when the change affects a user-visible path. Run `create-verification-skill` only when a user-visible path changed and the project has no `verify`. Run `code-review` against the review base. Record each skipped step as not applicable with the reason "medium change". A change that fails any medium test is big and gets the full playbook.
- Fix rounds: run the full `code-review` against the review base once. After fixing its findings, apply the comment rules and run `deslop` on the fix changes only, rerun affected checks, and commit. A finding is serious when it breaks behavior, loses data, touches security, privacy, money, or authentication, or shows a missing spec requirement. When no finding was serious, stop: record each fix and the check that proves it. When a finding was serious, run `code-review` again with the last reviewed commit as the fixed point. Repeat the fix-round review while it reports serious findings. Run the full review again only when a fix changes a public interface, a data model, or the approach. Fix a finding that is not serious only when the fix is cheap and local; otherwise record it as "not adopted" with a reason. Keep disposable test state, such as a test database or browser account, until the last fix round ends. Rerun only the affected paths. Then run the project's cleanup.
- When authorized work reaches PR creation, run [Opening a PR](../playbooks/opening-a-pr.md). The calling playbook finishes its checks first. Opening a PR does not run them; it reports what was and was not checked. If code changes after the checks, the calling playbook repeats the affected checks before the PR opens.
- Planning and Investigation finish their decision work, recommend the next implementation playbook, and wait for the user's request before changing code. Route added behavior to Feature, broken or slow behavior to Bug fix, and structural changes with preserved behavior to Refactoring.
